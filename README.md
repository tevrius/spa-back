# Складской учёт и планирование закупок

Демонстрационный REST API для спа-оператора. Остатки вычисляются из движений,
расход распределяется по FEFO, закупки рассчитываются детерминированно с
объяснением исходных данных и формул. LLM и автоматический заказ не входят в MVP.

## Запуск

Требуются Docker Engine / Docker Desktop и Docker Compose v2+.
Из корня репозитория:

```bash
docker compose up
```

Команда собирает сервис, дожидается PostgreSQL, применяет миграции Alembic,
загружает демоданные и запускает API. `.env` необязателен: предусмотрены
локальные демонстрационные значения по умолчанию.

- Swagger: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json
- ReDoc: http://localhost:8000/redoc
- Проверка БД и миграций: http://localhost:8000/health/ready
- Проверка процесса: http://localhost:8000/health/live

После изменения кода: `docker compose up --build`.
Остановка: `docker compose stop`. База сохраняется в именованном томе.
Повторный запуск не дублирует seed и не сдвигает его даты.
PostgreSQL не публикует порт на хост, API привязан к loopback.

## Тесты и стиль

Полная проверка с отдельной PostgreSQL, включая конкурентные запросы:

```bash
docker compose --profile test run --build --rm tests
```

Сервис `test-db` использует базу `warehouse_test` в tmpfs. Тесты очищают только
тестовую базу. Имя в `TEST_DATABASE_URL` должно заканчиваться на `_test`;
иначе очистка запрещена. Не используйте базу с ценными данными для тестирования.

Чистые расчёты без HTTP и БД:

```bash
docker compose --profile test run --build --rm --no-deps tests pytest tests/unit -p no:cacheprovider
```

Стиль:

```bash
docker compose --profile test run --rm --no-deps tests ruff check --no-cache app scripts tests alembic
docker compose --profile test run --rm --no-deps tests ruff format --no-cache --check app scripts tests alembic
```

Остановка тестовой БД: `docker compose --profile test stop test-db`.

Для разработки без контейнера: Python 3.11, `.venv` внутри репозитория,
`pip install -e '.[dev]'`, переменная `DATABASE_URL` на PostgreSQL, затем
`alembic upgrade head`, `python -m scripts.seed`, `uvicorn app.main:app`.
`pytest tests/unit` не требует БД; интеграционным тестам нужен отдельный
`TEST_DATABASE_URL`.

## Технологии и архитектура

- Python 3.11, FastAPI, Pydantic: типизированный HTTP-контракт и OpenAPI.
- SQLAlchemy 2 и psycopg: синхронные запросы и явные транзакции.
- PostgreSQL 16: MVCC, ограничения и транзакционные advisory-блокировки.
- Alembic: версионируемая схема, без `create_all` при запуске приложения.
- pytest и HTTPX/TestClient: доменные, API- и интеграционные проверки.
- Ruff: форматирование и статические проверки.

Прямые зависимости закреплены в `pyproject.toml`. Для промышленной поставки
следует дополнительно фиксировать транзитивные зависимости и digest образов.

```text
app/api/              маршруты, схемы и зависимости сессий
app/application/      сценарии учёта, прогноза и предупреждений
app/domain/           чистые FEFO, ledger replay и расчётные функции
app/infrastructure/   SQLAlchemy-модели и фабрика сессий
alembic/              миграции
scripts/              запуск миграций и идемпотентный seed
tests/unit/           расчёты без HTTP и БД
tests/integration/    API, транзакции, конкуренция и миграции
```

Доменный модуль не зависит от HTTP, ORM, окружения или текущего времени.
Дата расчёта передаётся явно. Чтение использует единый снимок
`REPEATABLE READ READ ONLY`, чтобы показатели ответа были согласованы.
Запись использует `READ COMMITTED`: после ожидания блокировки видит
результат предыдущего писателя.

## Модель учёта

- `products`, `locations`: справочники; у товара единица измерения, упаковка,
  минимальный заказ и срок поставки. Валюта одна — RUB.
- `batches`: партия SKU в объекте, первый приход, срок годности, цена.
- `movements`: исходные операции с уникальными номерами документов.
- `movement_allocations`: производное распределение изменений по партиям.
- `purchase_orders`, `purchase_order_items`: ожидаемые поставки и полученное количество.

Остаток партии = `SUM(movement_allocations.delta)`. Заголовок движения повторно
не суммируется. Отдельного изменяемого поля остатка нет.
FEFO: `expires_on`, затем `received_on`, затем `id`. Товар пригоден включительно
по дату годности. При расходе партию выбирает система.

Операции по SKU–объект блокируются через `pg_advisory_xact_lock` до конца
транзакции. Создание движения, партии, перераспределение и расчёт ответа атомарны.
Недостаток запаса откатывает всю операцию. Номер документа защищён также UNIQUE
в PostgreSQL, включая одновременную загрузку в разных объектах.

Операции задним числом разрешены. История пары пересчитывается по `(date, id)`:
проверяется пригодность и достаточность запаса на каждом шаге. Поздно внесённый
приход может изменить распределение более позднего расхода, но не его исходные
данные. Исторический недостаток отклоняет новую запись целиком.
В пределах одной даты используется порядок ID: нельзя вставить приход перед
ранее зарегистрированным расходом того же дня. Распределения являются
пересчитываемым представлением, а не юридическим журналом.

| Операция | Количество | Значение |
|---|---|---|
| `receipt` | положительное | Приход в новую или существующую партию |
| `consume` | положительное | Расход по FEFO, поле партии запрещено |
| `writeoff` | положительное | Списание указанной партии, включая просроченную |
| `return` | положительное | Возврат материала на склад в указанную партию |
| `correction` | ненулевое знаковое | Изменение количества, не установка абсолютного остатка |

Возврат поставщику и карантин не моделируются. Возврат в просроченную партию
увеличивает учётный, но не пригодный запас. Просрочка не списывается автоматически:
нужен `writeoff` на оставшееся количество. Ни одна операция не может сделать
остаток партии отрицательным.

Документ соответствует одному движению, его номер глобально уникален согласно
ТЗ. Для многострочных документов потребуется отдельный заголовок и ключ строки.
Количество имеет точность 0.001, цена — 0.01; более точный ввод отклоняется.
Деньги и количества: `Decimal`, хранение: `NUMERIC`. Календарная симуляция
использует точные рациональные числа `Fraction`, чтобы периодическая дробь
расхода за 90 дней не создавала ложный дефицит и лишнюю упаковку заказа.
Основные поля JSON — числа; точные промежуточные значения в explanation
могут быть строками десятичных или рациональных чисел (например, `1/90`).

## API

### POST /api/movements

Приход (подставьте сегодняшнюю или прошлую дату):

```json
{
  "date": "2026-09-23",
  "sku": "OIL-001",
  "location": "MS-01",
  "operation": "receipt",
  "quantity": 20,
  "batch": "OIL-NEW",
  "document_number": "IN-2026-001",
  "expires_on": "2027-09-23",
  "unit_price": 1259.05
}
```

У новой партии обязательны `expires_on` и `unit_price`. Для существующей их
можно опустить; переданные значения должны совпадать. Срок годности не раньше
прихода. Приход по другой цене требует другого кода партии.

Расход:

```json
{
  "date": "2026-09-23",
  "sku": "OIL-001",
  "location": "MS-01",
  "operation": "consume",
  "quantity": 3.5,
  "document_number": "USE-2026-001"
}
```

Ответ `201`: ID, исходные поля, `allocations` с партиями и знаковыми изменениями,
`current_stock` и `available_stock`. Будущее определяется в `APP_TIMEZONE`.

### GET /api/movements

Фильтры: `sku`, `location`, `operation`, `date_from`, `date_to` (включительно).
Пагинация: `limit` 1–100, по умолчанию 50; `offset` от 0.
Ответ: `{items, limit, offset, total}`, порядок по дате и ID убыванию.

```bash
curl 'http://localhost:8000/api/movements?sku=OIL-001&location=MS-01&operation=consume&limit=5'
```

### GET /api/stock

Фильтры `sku`, `location`, пагинация как у движений. Возвращаются пары с заведёнными
партиями, включая нулевые остатки. Неиспользованные комбинации всех SKU и объектов
не создаются искусственно.

- `current_stock`: учётный остаток, включая ещё не списанную просрочку.
- `available_stock`: пригодное для расхода количество.
- `expired_stock`: разница этих величин.
- `avg_daily_consumption`: `consume` за 90 полных дней до сегодня, делённый на 90.
- `days_of_stock`: доступный запас / средний расход; `null` при нулевом расходе.
- `nearest_expiry`: ближайший срок партии с положительным остатком, включая
  просроченные; `null`, если все партии пусты.

```bash
curl 'http://localhost:8000/api/stock?location=MS-01'
```

### GET /api/stock/{sku}

Объекты, показатели и партии: количество, даты, цена, все приходные документы.
Известный товар без партий возвращает `locations: []`.

```bash
curl 'http://localhost:8000/api/stock/OIL-001'
```

### POST /api/forecast

```bash
curl -X POST http://localhost:8000/api/forecast \
  -H 'Content-Type: application/json' \
  -d '{"sku":"OIL-001","location":"MS-01","months":3,"safety_stock_days":14}'
```

Ровно один горизонт: `days` (1–366) или `months` (1–12).
`start_date` по умолчанию сегодня, допускается в следующие 366 дней.
Страховой запас — 0–366 дней, по умолчанию 14. Месяцы календарные: прибавляем
месяцы к началу, ограничивая день последним днём целевого месяца.
`period.to` включительно. Например, с 1 октября на 3 месяца — по 31 декабря.

```text
D = consume за [сегодня − 90 дней, сегодня) / 90
F = D × дни выбранного периода
SS = D × страховые дни
ROP = D × (срок поставки + страховые дни)
```

В простом случае: `Qraw = max(0, F + SS − доступный остаток − поставки)`.
В общем случае прогноз идёт по дням от сегодня до конца периода:

1. Исключаем истёкший запас, добавляем сегодняшние поставки.
2. Выполняем прогнозный расход по FEFO, фиксируем непокрытый спрос.
3. `Qraw = непокрытый спрос + max(0, SS − конечный остаток)`.
4. Если `Qraw > 0`: `Q = ceil(max(Qraw, minimum_order) / pack_size) × pack_size`.
   Если потребность нулевая, заказ тоже нулевой.

Это консервативная рекомендация: поздняя поставка не компенсирует уже пропущенный
спрос. Отложенный старт учитывает также дефицит до выбранного периода;
`forecast_demand` относится только к периоду, `bridge_demand` в explanation —
к промежутку до него. Входящий объём включает поставки от сегодня до конца
периода, в том числе до его начала.

Учитываются неполученные части открытых заказов. Отменённые и полученные
исключены; просроченные по дате дают предупреждение и не считаются гарантированными.
CRUD заказов не требуется ТЗ: есть модель и seed. Приход не закрывает заказ
автоматически: контракт движения не содержит его ID.

`stockout_date` — первый день непокрытого спроса без новой закупки, только в
расчётном горизонте; иначе `null`. Дата заказа — день достижения страхового
запаса минус срок поставки, не раньше сегодня. Если обычная поставка опоздает,
возвращается `expedite_required`. При нулевой закупке дата заказа — `null`.

Цена берётся из последнего по `(дата, ID)` прихода SKU на этот объект.
Нет прихода — цена и стоимость `null` с предупреждением. Стоимость округляется
HALF_UP до 0.01, расчётные количества для показа — до 0.001. Промежуточные
формулы используют неокруглённые значения.

`explanation` содержит дату, окно истории, исходные значения, поставки,
формулы и допущения. При неполной истории предупреждение обязательно,
знаменатель остаётся 90 согласно ТЗ. Возвраты, списания и корректировки не считаются
спросом. Новая закупка — агрегированный объём, график надо согласовать с поставщиком.

### GET /api/alerts

Фильтры `sku`, `location`, пагинация. Сортировка: важность, SKU, объект, код, партия.
Каждое предупреждение содержит `code`, `level`, `message`, `metrics`.

- `stock_shortage` / critical: доступного запаса меньше расхода за срок поставки.
  Буквальное правило ТЗ без входящих заказов; они учитываются в forecast.
- `expiring_batch` / warning: положительный запас с близким сроком годности.
- `expired_batch` / critical: просроченный остаток требует `writeoff`.
- `no_movement` / info: нет любых операций не менее порогового числа дней.
- `never_moved` / info: нет истории вообще; объект `null`, выводится только
  без фильтра по объекту, поскольку привязка неизвестна.

```bash
curl 'http://localhost:8000/api/alerts?location=MS-01'
```

## Ошибки

```json
{
  "error": {
    "code": "insufficient_stock",
    "message": "Consumption exceeds usable stock",
    "details": {"requested": "12", "available": "10", "operation_date": "2026-09-23"}
  }
}
```

| Статус | Причина |
|---|---|
| 400 | Синтаксически неверный JSON |
| 404 | Неизвестный SKU, объект или партия в выбранном объекте |
| 409 | Повторный номер документа |
| 422 | Валидация, будущее, недостаток запаса, конфликт метаданных, неверный период |
| 503 | База временно недоступна |

Лишние поля тела запрещены. Ошибка не раскрывает всё тело запроса и внутренние
исключения. При заднем числе недостаток может относиться к последующему движению:
его дата указана в `details`.

## Окружение

Настройки считываются из окружения и необязательного `.env`, созданного на основе
`.env.example`. `.env` не коммитится.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `POSTGRES_DB` | `warehouse` | Основная БД |
| `POSTGRES_USER` | `warehouse` | Пользователь БД |
| `POSTGRES_PASSWORD` | `warehouse_demo` | Пароль локального демо |
| `DATABASE_URL` | URL с хостом `db` из примера | Подключение SQLAlchemy/psycopg |
| `API_PORT` | `8000` | Порт API на localhost |
| `APP_TIMEZONE` | `Europe/Moscow` | Текущая бизнес-дата |
| `EXPIRY_WARNING_DAYS` | `30` | Порог близкой годности |
| `INACTIVITY_DAYS` | `90` | Порог отсутствия движений |
| `SEED_DEMO` | `true` | Seed при запуске |

При изменении реквизитов БД обновите и `DATABASE_URL`. Переменные `POSTGRES_*`
инициализируют новую БД и не меняют пароль пользователя в уже существующем томе.

## Демоданные и ограничения

Два объекта, масло с историей расхода и открытым заказом, маска с дефицитом
и просрочкой, соль без недавних движений, новый товар без истории.
Даты рассчитываются относительно первого запуска и затем сохраняются.

- Нет авторизации, UI/LLM, сезонности, НДС, валютного пересчёта и бюджетного лимита.
- У товара один набор условий поставки. Справочники и заказы загружаются seed.
- Прогноз предполагает постоянный спрос. Будущие поставки с неизвестной годностью
  считаются пригодными до конца горизонта. Это не оптимизатор графика заказов.
- При записи пересчитывается вся история SKU–объект: для больших объёмов нужны
  контрольные снимки и ограниченное окно пересчёта.
- Агрегаты склада и предупреждений строятся до пагинации; рассчитано на MVP.
- Для регулируемого учёта нужен аудит версий распределений и закрытие периодов.
- Полученный обратно материал не проходит отдельную проверку качества/карантин.

Развитие: роли и авторизация, аудит, справочные API, связь заказов и приходов,
метрики, многострочные документы, прогноз загрузки, инструменты для LLM поверх
API. Даже с ИИ расчёт чисел должен оставаться детерминированным.

## Мотивация участия

Интерес к проекту, роль в команде, часы в неделю и длительность участия заполняет
кандидат лично. Ответы не генерируются от его имени.
